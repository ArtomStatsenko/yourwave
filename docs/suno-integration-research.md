# Suno → PersonalRadio: исследование интеграции

Проверено 26 октября 2026 года. Цель — активный эфир из обновляемой Suno-библиотеки, с очередью, ведущим и историей PersonalRadio. Это исследование и проект эксперимента: реализация, установка сторонних сервисов и включение функций не выполнялись.

## Решение

**Готового подтверждённого решения «подключить текущий Suno-аккаунт и устойчиво играть новые треки в PersonalRadio» пока нет.** Существует официальный API-вход, но доступ для данного аккаунта не подтверждён. Два готовых радиопроекта используют старый способ получения аудио. Более свежий неофициальный адаптер реализует текущий защищённый playback, однако не является потоковым сервером и требует отдельной оценки безопасности и условий использования.

Рекомендация — эксперимент **Suno Live Library**, где PersonalRadio синхронизирует выбранный каталог и сам планирует эфир, а разрешённый источник аудио подготавливает следующие треки заранее. Для полноценного online-режима первый выбор — официальный доступ с подтверждёнными правами чтения существующих clips; до его появления рабочий ограниченный вариант — привязка живого каталога к уже разрешённым локальным загрузкам. Не выдавать этот ограниченный вариант за прямой streaming. Современный community playback годится только как отдельный технический кандидат, а не как доверенный готовый источник эфира.

## 1. Что реально проверено

| Проверка | Результат | Что доказывает / не доказывает |
|---|---|---|

| Воспроизведение свежего V6-трека | Плеер перешёл в `paused=false`, время росло; длительность около 223 секунд, источник `blob:https://suno.com/...`; затем тест остановлен | Браузерное воспроизведение подтверждено состоянием плеера; физическое прослушивание не проводилось |

| Публичный playlist endpoint, который использует Raydio | Один GET без авторизации вернул HTTP 403 | Доступ по этому маршруту не подтверждён; один ответ не доказывает недоступность всех публичных плейлистов |
| Официальный Platform, вход через Google | Доступен выбор Google-аккаунта; ни один не выбран, поскольку пользователь использует Apple/Microsoft | Лишняя Google-учётка не привязывалась |
| Официальный Platform, вход по email текущего Suno | Сервер: `Email sign-in is not enabled for this address yet. Sign in with Google, or contact your account administrator.` | Этот путь входа для текущего адреса сейчас закрыт; это не доказательство отсутствия API у Suno вообще |
| Неавторизованный GET `api.suno.com/v0/audio` | HTTP 404 | Только диагностический факт; без официального контракта и ключа вывод о поддерживаемых endpoints делать нельзя |
| Четыре community-проекта | Прочитаны исходники закреплённых commits, зависимости, тесты и настройки | Их live-авторизация, тесты и длительная работа здесь не запускались |

Проверки аудио выполнены в этой беседе 26.10.2026, отдельно от работающего радио. В отчёт не включены адрес аккаунта, даты рождения, cookies, OAuth-идентификаторы, токены или пользовательские ссылки на библиотеку.

## 2. Официальный Suno Platform

[Официальная страница](https://platform.suno.com/) действительно рекламирует REST API для генерации песен, covers и mashups. На публичной странице нет контракта чтения пользовательской библиотеки, playlist sync, цены, квот или гарантии, что обычная Pro/Premier-подписка включает API. Интерфейс предлагает Google или код на email; результат проверки текущего адреса описан выше.

Следовательно, уточнить надо не только выдачу ключа, но и четыре конкретные возможности: доступ к существующим clips обычного аккаунта; чтение выбранного плейлиста с пагинацией; разрешённая внешняя доставка аудио; права на воспроизведение и временное хранение для персонального радио. Доступный API генерации сам по себе не отвечает на эти вопросы.

Есть [интеграторская документация TheDAWSound](https://github.com/DemonbreunDELLC/TheDAWSound/blob/main/docs/guides/SUNO_EXTERNAL_API.md) с описанием `api.suno.com`, асинхронной генерации и streaming-статуса. Это материал другого разработчика о его интеграции, **не официальный контракт Suno**, поэтому его endpoints, цены, задержки и доступность не приняты за подтверждённые возможности нашего аккаунта.

**Вердикт:** предпочтительный поставщик при получении подходящего доступа; прямо сейчас не готовая интеграция существующей библиотеки.

## 3. Сравнение готовых вариантов

Подробная проверка исходников с commit SHA, ссылками на функции, зависимостями и найденными рисками: [техническое приложение](research/suno-adapters-2026-10-26.md).

| Вариант | Что даёт | Критическое ограничение | Решение для PersonalRadio |
|---|---|---|---|
| [Suno Platform](https://platform.suno.com/) | Официальная API-площадка, заявлена генерация | Доступ текущего аккаунта и чтение старой библиотеки не подтверждены | Первый выбор после проверки доступа и контракта |
| [Raydio](https://github.com/hellodword/raydio) | Отдельное web-radio, синхронизация плейлистов, MP3-кэш, общий план | Использует `audio_url`, не обрабатывает актуальный защищённый playback | Не разворачивать рядом второй радиодвижок |
| [sunyujingmusic-alt/unofficial-suno-api](https://github.com/sunyujingmusic-alt/unofficial-suno-api) | Текущий playback через пользовательскую сессию | Полная загрузка трека перед ответом; legacy-only clips отвергаются; нет live-доказательства здесь | Только кандидат для отдельного изолированного прототипа |
| [gcui-art/suno-api](https://github.com/gcui-art/suno-api) | Популярная оболочка внутренних Suno-функций | Нет нового playback; заметная браузерная/CAPTCHA-инфраструктура | Не выбирать для этой задачи |
| [Suno Radio Bot](https://github.com/kphillipsdev/suno-radio-bot) | Discord-radio, autofill, запросы и очередь | Старый `audio_url`/MP3 fallback; Discord вместо источника Liquidsoap | Не выбирать для PersonalRadio |
| [OmnAPI](https://docs.omnapi.com/guides/suno-playback/) | Managed generation/playback с API key | Связь с частной библиотекой нашего Suno не подтверждена; отдельный поставщик и биллинг | Рассматривать только после проверки конкретных clip IDs и условий |
| [KIE](https://docs.kie.ai/suno-api/recovery-audio) / [SunoAPI.org](https://sunoapi.org/) | Платные API генерации и доставки результатов | Нельзя считать официальными Suno; перенос текущей личной библиотеки не подтверждён | Не покупать как решение задачи синхронизации библиотеки |
| [Castloop](https://www.castloop.tv/faq.html) | Зацикливание загруженного видео в RTMP 24/7 | В FAQ описан upload видео, а не чтение Suno-библиотеки | Другая задача; нашему эфиру не нужен |
| Браузер Suno + захват звука | Оригинальный web-player реально работает | Управление треками, сон/сессия/паузы браузера; условия Suno запрещают recording/stream ripping | Не рекомендую как основу эксперимента |

### Почему не Raydio

У него уже есть radio timeline и кэш, но это те же обязанности, что выполняет PersonalRadio. Внедрение целой системы добавит второй каталог и планирование, а форматный блокер останется. В проверенном worker синхронизация по умолчанию раз в 30 минут, пагинации playlist API нет, исчезнувшие из ответа ранее управляемые файлы удаляются. Нельзя переносить эту схему удаления в нашу библиотеку: ошибка или частичный ответ не должны стирать музыку. Отдельная лицензия на код в снимке не найдена. Источники и границы вывода приведены в приложении.

### Что полезно в новом unofficial fork

Он действительно содержит современный playback-механизм, но не обещает маленькую задержку запуска: сначала получает целый файл в память, лимит 100 MiB, timeout 120 секунд. Это допустимая модель **предподготовки**, если её вынести из критического пути переключения музыки; это не доказательство бесконечного прямого потока.

Полное приложение нельзя считать узким read-only адаптером: оно содержит и платные/изменяющие операции, использует сессию владельца, не требует отдельного client key на routes и разрешает широкий CORS. Изоляция localhost полезна, но не заменяет защиту endpoints. В общем HTTP-клиенте найдено автоматическое добавление Bearer к запросам, включая медиа; для возможного адаптера API и CDN должны иметь разные правила credentials. Наличие этих мест в исходнике не означает, что здесь произошла утечка: приложение не запускалось.

### Что реально обещают managed API

[OmnAPI playback](https://docs.omnapi.com/guides/suno-playback/) описывает готовый contract: текущий playback URL, состояния подготовки/воспроизведения, MIME, срок действия и восстановление после ошибок; есть режим раннего chunked MP3. [Clip reads](https://docs.omnapi.com/guides/suno-reads/) принимают внешние Suno clip IDs, различают доступ к ресурсам; это интереснее простого generation API. Однако возможность прочитать публичный clip **не подтверждает** доступ к частной библиотеке, право ретрансляции или передачу owner-сессии Suno. Нужен конкретный live-тест с ключом данного провайдера; такой ключ не вводился.

[Storage policy](https://docs.omnapi.com/guides/suno-storage/) отделяет retention ресурсов от срока жизни URL; хранить один URL как постоянную запись каталога нельзя. Это ещё один поставщик с собственным договором и состоянием, а не замена обычной Suno-подписки.

[KIE recovery](https://docs.kie.ai/suno-api/recovery-audio) восстанавливает аудио результатов ранее созданного generation task. Из этого не следует поддержка произвольного Suno-плейлиста пользователя. На [SunoAPI.org](https://sunoapi.org/) опубликованы собственные пакеты API-кредитов; не установлено, что они дают доступ к нашей библиотеке или связаны с лимитами обычной подписки Suno. Маркетинговые заявления о стабильности не принимались за runtime-доказательство.

## 4. Условия использования, влияющие на выбор

[Условия Suno](https://suno.com/terms), действующие с 03.09.2026, связывают разрешённое коммерческое использование с одобренным Download и отдельно запрещают получение копии иными каналами, включая recording и stream ripping. Поэтому наличие оплаченного аккаунта или возможности декодирования не равнозначно разрешению внешнего копирования/эфира; браузерный захват из прежнего предложения исключён. Это чтение опубликованных условий, а не отдельное юридическое заключение; для партнёрского API нужен его применимый контракт.

В текущем UI обычного аккаунта осталось **0 загрузок**. Это не означает, что уже официально скачанные файлы нельзя воспроизводить, и не устанавливает размер отдельной API-квоты. Это означает, что проект автоматического получения новых файлов нельзя строить на предположении о неограниченных обычных Downloads. Покупки, генерации и экспорт не выполнялись.

## 5. Рекомендуемый эксперимент: Suno Live Library

### Пользовательское поведение

В Experiments — выключенный по умолчанию переключатель `Suno Live Library`. Пользователь выбирает один плейлист; радио периодически обновляет полный каталог, подхватывает новые завершённые треки и сохраняет приоритет не звучавших. Оно показывает число найденных, готовых и недоступных треков, последний успешный sync и состояние подключения. Частота 2–5 минут — стартовая инженерная настройка, **не подтверждённый лимит Suno**; фактический интервал должен учитывать условия поставщика и `Retry-After`.

Трек не считается готовым по наличию URL или HTTP 200. Следующие один-два трека заранее доступны как проверенное разрешённое аудио. Ведущий, джинглы, кроссфейд, Next, перестановки, история и timeline принадлежат PersonalRadio. Ошибка Suno не останавливает уже играющий трек; при отсутствии следующего готового трека работает существующий локальный fallback. UI честно различает выбранный источник и реально звучащий.

### Откуда брать аудио

1. **Предпочтительно:** официальный API с подтверждённым чтением существующих clips и разрешённым внешним воспроизведением/буферизацией. Если он умеет лишь генерировать новые песни, это отдельная функция, а не решение этой задачи.
2. **Ограниченный вариант уже сейчас:** живой каталог/список пожеланий плюс явное соответствие Suno clip ID → ранее официально скачанный файл. Новые неготовые записи видны, но не объявляются готовыми и не создают тишину. Сопоставление не должно угадывать по одному title: одноимённые версии — разные clips. Доступность устойчивого discovery ещё требует проверки: протестированный публичный endpoint дал 403.
3. **Исследовательский кандидат:** современный unofficial playback. Только локальный ограниченный smoke после установления допустимого способа использования; не внедрять весь Next.js server и не давать ему generation/export-поверхность. Техническое извлечение аудио не снимает вопрос условий Suno.

### Где потребуется изменение текущего кода

Это карта области изменения, не выполненный рефакторинг:

| Область | Текущий факт | Требуемое поведение |
|---|---|---|
| `radio/plugins.py` | Есть `PLUGINS`, `EXPERIMENTS`, saved switches | Новый выключенный эксперимент; доступность источника отдельно от его выбора |
| `radio/settings.py`, `radio/config.py` | Источники только `local` / `ytmusic`; `music_source()` связан с yt-флагом | Явный третий источник с собственной проверкой доступности |
| `radio/ui.py`, `radio/ui.html` | YT-specific connection/status и подписи | Локальное подключение, playlist selector, readiness/sync/error, фактический источник |
| Новый небольшой `radio/suno.py` | Готового Suno-адаптера нет | Каталог по стабильным IDs, пагинация/atomic manifest, проверенный разрешённый audio resolver |
| `radio/daemon.py` | Много binary local/YT условий | Source selection, очередь, unplayed, reroll, current/target и ошибки должны знать Suno |
| `radio/engine.py`, `radio/radio.liq` | YT protocol, загрузка и fallback уже существуют | Переиспользовать жизненный цикл requests и fallback; не приравнивать Suno к YT |
| `radio/music.py`, `radio/timeline.py`, `radio/hooks.py` | Метаданные, replay и previews местами знают только `ytmusic:` | Корректные labels/duration/history; replay только при доступном аудио; Songle не отправлять Suno-ID |
| `tests/test_music_source.py`, `tests/test_ytmusic.py` и новый узкий тест Suno | Уже есть source/fallback регрессии | Disabled path, третий источник, неполный sync, 401/403/429, пустой/недекодируемый файл и правдивый статус |

Нельзя просто добавить `suno` в select: binary logic начнёт показывать его как Local или выбирать неподходящую библиотеку. При этом нет причины заранее строить plugin-framework: достаточно исправить конкретные границы трёх источников и сохранить существующие интерфейсы.

### Минимальный набор доказательств перед включением

1. Авторизованное чтение выбранного каталога без изменения библиотеки; все страницы, повторный sync, частичный ответ не удаляет записи/файлы. Один новый завершённый clip появляется в пределах выбранного интервала.
2. Три разных свежих разрешённых трека плюс один старый: фактическое аудио, декодируемый контейнер, правдоподобная длительность и ненулевая энергия. Отдельно измерить получение первого звука и полного файла, не подменять их общей HTTP-задержкой.
3. Изолированный `RADIO_DATA_DIR`; тот же путь Liquidsoap → локальный stream/запись, с проверкой ненулевого звука, затем прослушивание. Не считать `ready`, URL или queued state доказательством эфира.
4. Переходы Local → Suno → Local на границе трека, Next/reroll, ведущий, история и timeline. Ошибки авторизации, 429, timeout и пустая очередь сохраняют звук через локальный fallback и показывают его реальный источник.
5. Возобновление сессии и повторный запуск без дубликатов, осиротевших временных файлов и утечки секретов. Продолжительный прогон с несколькими обновлениями каталога; до него не заявлять устойчивость 24/7.

## 6. Что исправлено относительно предыдущих ответов

- Наличие CDN URL не означало декодируемое аудио: проверка это опровергла.
- Захват браузера не единственный технический вариант: существует современный community playback, но его полная загрузка и условия использования меняют оценку.
- Raydio нельзя рекомендовать только по README: его конкретный downloader не поддерживает новый формат.
- Наличие официального API-портала не означает, что обычный аккаунт имеет API-доступ или что API читает его старую библиотеку.

Получен анализ официального интерфейса, документов поставщиков, четырёх code snapshots и наблюдавшегося аудиопути. Сторонние сервисы не установлены и не запущены, API-ключи не создавались, cookie не извлекались, кредиты не тратились. Нового эксперимента, переключателя или изменённого радиоэфира пока нет; изменены только исследовательские документы.
