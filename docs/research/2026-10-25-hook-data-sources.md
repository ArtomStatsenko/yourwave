# Готовые разметки хуков: источники, идентичность записи и ограничения

Проверено 2026-10-25 по официальным документации, репозиториям и публичным ответам API; исследование без установки инструментов и изменений эфира. Предложения ниже — проектные решения, а не новые результаты прослушивания.

## Главное для реализации

**Разделить три задачи:** идентифицировать запись → получить/построить разметку секций → выбрать и проверить короткую фразу. Название песни, MusicBrainz ID, AcoustID и даже метка `chorus` по отдельности не доказывают, что нужные секунды подходят локальному файлу. MusicBrainz намеренно объединяет некоторые различия тишины, фейдов, скорости и мастеринга в одну Recording; поэтому один MBID недостаточен для переноса cue-точек. [Правила Recording](https://musicbrainz.org/doc/Style/Recording)

Для carbonara текущий глобальный текст→ASR-путь уже дал четыре приемлемых выбранных аудиофайла (одна новая оценка и три byte-identical старым); новый фонетический aligner не следует делать обязательным до проверки этой схемы на новых треках. Подробности локального эксперимента: [ALIGNMENT-REPORT](../../spike/music-hooks/results/carbonara/ALIGNMENT-REPORT.md).

## Songle: работающий источник с условиями использования

Официальный REST API предоставляет поиск по `q`, сведения по URL исходной песни/видео, `chorus` и список `chorus_revisions`; разметку можно запросить с `revision_id`. Документированы ответы 404 для незарегистрированного URL и 500 для ошибки сервера. [API v1](https://widget.songle.jp/docs/v1?lang=en)

В этой проверке официальный пример реально вернул JSON припевов и JSON ревизий: это подтверждает доступность этих конкретных запросов, а не наличие SLA или всего каталога. В ответе `chorusSegments[].repeats[]` хранятся `start` и `duration`; пример 63938.5 означает 63.9385 секунды, то есть перед нормализацией делим на 1000. [Ответ chorus](https://widget.songle.jp/api/v1/song/chorus.json?url=www.youtube.com%2Fwatch%3Fv%3DPqJNc9KVIZE), [ответ revisions](https://widget.songle.jp/api/v1/song/chorus_revisions.json?url=www.youtube.com%2Fwatch%3Fv%3DPqJNc9KVIZE)

Практика: сохранять исходный URL, полученную ревизию/идентификатор выбранной разметки, время получения, сырые единицы и нормализованные секунды; пользовательское одобрение локального фрагмента не заменять автоматически новой ревизией. API не возвращает готовую гарантию «лучший FM-хук»: из секции всё ещё надо выбрать фразу. Это проектный вывод из схемы ответа, а не заявленная функция сервиса.

**Важное ограничение:** условия называют Songle Widget исследовательской системой, которую можно изменить/остановить без предупреждения; встроенный плеер должен быть видим, а для коммерческого применения (включая бесплатные сервисы компаний) предлагается связаться с авторами. Эти требования явно относятся к внешнему плееру; я не нашёл в этих условиях отдельной явной лицензии на массовое зеркалирование всей REST-разметки. Не надо ни распространять запрет скрытого *виджета* на любой backend-запрос без основания, ни считать ответ API разрешением на любой экспорт. Для первой версии — точечные обращения в личном эксперименте, ссылка на источник, без скрытого встраивания виджета и без зеркала каталога. [Условия](https://widget.songle.jp/docs/terms-of-use)

Числового публичного лимита REST-запросов и гарантии регистрации без аккаунта в прочитанной документации не обнаружено; поэтому «1 запрос/с», таймаут, backoff и кэш отсутствия — наша консервативная политика, не квота поставщика. Автоматическую массовую регистрацию песен не закладывать.

## AcoustID и MusicBrainz: помогают найти запись, не припев

AcoustID принимает Chromaprint-отпечаток и **длительность всего файла в секундах**, возвращает совпадения и связанные метаданные/recording IDs. Для приложения нужен собственный зарегистрированный `client` API key; примерный ключ нельзя встраивать в рабочий продукт. Бесплатный сервис предназначен для некоммерческого применения, лимит — максимум 3 запроса/с. Отдельное право на submit не нужно для lookup; в проекте достаточно lookup, автоматически публиковать отпечатки не надо. [Официальный web service](https://acoustid.org/webservice)

Данные AcoustID имеют CC BY-SA 3.0, за исключением отображения MusicBrainz↔AcoustID под CC0; это лицензия данных, а не гарантия доступа/бесплатности любого использования сервиса. [База и лицензии](https://acoustid.org/database)

MusicBrainz следует запрашивать с осмысленным User-Agent и не чаще одного запроса/с на IP без иной договорённости. MBID — идентификатор сущности записи, а не фиксированной PCM-шкалы: различающиеся тишина/фейды/мастеринг могут оставаться одной Recording. [API rate limiting](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting), [Recording style](https://musicbrainz.org/doc/Style/Recording)

**Вывод:** `local hash/decoded-audio signature` — ключ одобренных секунд; `YouTube ID` или `AcoustID→MBID` — ключ поиска внешней записи. Совпадение MBID не заменяет сравнение длины и аудиосопоставление. Если версия другая, сначала перенос таймкодов по аудио (например, уже испытанный DTW), затем повторная проверка фразы; при сомнении чужие секунды не использовать. Это проектная политика, не гарантия fingerprint-поставщика.

## Нужен ли настоящий acoustic forced alignment

| Вариант | Что подтверждено первичными источниками | Применение здесь |
| --- | --- | --- |
| **WhisperX** | Сочетает ASR с wav2vec2 phoneme alignment; модели зависят от языка, слова вне словаря могут остаться без времени, перекрывающаяся речь обрабатывается плохо. Документация описывает речь, не гарантирует качество пения под инструментами. [README](https://github.com/m-bain/whisperX) | Первый отдельный A/B-кандидат при реальной проблеме границ; не добавлять diarization, если она не нужна. На carbonara/Mac ещё не запускали. |
| **Montreal Forced Aligner** | Сопоставляет корпус и текст с произносительным словарём и акустической моделью; возможно адаптировать/обучить модель. В 3.4 меняется формат моделей и путь HF-команд, поэтому команды надо фиксировать по версии. [Workflow](https://montreal-forced-aligner.readthedocs.io/en/latest/user_guide/workflows/alignment.html) | Больше настройки произношений/модели; полезнее при подготовленном вокальном корпусе, чем как первый дополнительный dependency. Готового подтверждённого singing quality в просмотренной документации не найдено. |
| **CTC через TorchAudio** | Исторический API `forced_align` существовал с CPU/CUDA-реализацией, но официальная актуальная документация сообщает: deprecated в 2.8, удалён в 2.9. [Предупреждение tutorial](https://docs.pytorch.org/audio/stable/tutorials/ctc_forced_alignment_api_tutorial.html) | Не строить новую обязательную интеграцию вокруг устаревшего примера без закреплённой старой среды. Если испытывать — отдельный процесс/окружение, без обновления рабочего радио. |

Пока выбор: сохранять нынешнее полное выравнивание текста→ASR как дешёвый основной путь для carbonara, измерить ошибки на новых 12–20 песнях; только если осталось много срезанных/смещённых слов — сравнивать WhisperX на том же фиксированном наборе. Отделение вокала от аккомпанемента можно испытать как дополнительный вариант для сложных записей, но это пока гипотеза, не проверенный шаг нашего пайплайна.

## Пригодность и фолбэки

1. Уже одобренный cue той же локальной записи имеет приоритет; переобучение/обновление базы не должно молча менять его.
2. Для встроенного полного текста — сохранение порядка секций; для внешних аннотаций — точная идентичность/перенос времени; затем качество фразы проверяется отдельно.
3. 404/«нет разметки» и 429/5xx/timeout — разные состояния: первое можно отрицательно кэшировать, второе отложить с backoff. Сроки кэша — наша настройка, не заявленная гарантия провайдеров.
4. Отказ всех источников должен означать «анонс без фрагмента» либо пропуск анонса; музыка продолжает играть. Не заменять это случайным процентом длительности песни.

Не проверены массовый охват фонотеки новыми датасетами, singing-качество WhisperX/MFA, прямой AcoustID lookup с рабочим ключом и эфирная интеграция. Лицензии аннотаций не следует трактовать как права на распространение исходной музыки.
