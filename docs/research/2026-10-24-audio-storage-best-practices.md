# Хранение базового аудио и очистка истории

Проверено 24 октября 2026 по первичным источникам. Это исследование; история и GitHub не изменялись.

## Решение для PersonalRadio

Можно сохранить нынешний GitHub-репозиторий и его историю разработки, удалив аудиофайлы из всей публикуемой истории через `git-filter-repo`. Новый корневой снимок — альтернатива, а не обязательное условие. GitHub рекомендует `git-filter-repo` для удаления файлов из прежних коммитов. Простое удаление WAV новым коммитом оставляет прежние версии доступными. [GitHub: удаление файлов из истории](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github).

Базовый комплект предлагаю раздавать одним версионированным архивом в **GitHub Releases того же репозитория**, хранить в Git только код, документацию, манифест, SHA-256, лицензию и атрибуцию. В текущем `assets/` четыре WAV занимают 3 586 310 байт: лимиты не требуют вынесения, это решение об отделении готовых ресурсов от исходников. GitHub прямо предлагает Releases для распространения бинарных файлов; отдельный asset должен быть меньше 2 GiB, общий размер релиза и трафик не ограничены. [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

## Сравнение вариантов

| Вариант | Когда подходит | Вывод для проекта |
| --- | --- | --- |
| Обычный Git | Небольшие ресурсы редко меняются; нужен готовый клон | Технически допустим, но не соответствует пожеланию хранить сет отдельно |
| GitHub Release asset | Готовый комплект с собственной версией | Рекомендую: код и набор обновляются независимо |
| Git LFS | Бинарники нужно версионировать вместе с рабочими коммитами | Сейчас лишний механизм: указатели, получение объектов и отдельные квоты |
| Оригинальный MP3 + локальная сборка | Проверяемое происхождение и возможность пересобрать | Оставить запасным путём через существующий `tools/build_base_audio.py` |

Это проектная рекомендация. LFS хранит в Git указатели на внешние объекты, а объекты и скачивания учитываются отдельно; изменение файла добавляет в хранение полную новую версию. Перенос в LFS сам по себе не устраняет проблему прежних Git-коммитов. [Устройство Git LFS](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage), [квоты и учёт](https://docs.github.com/en/billing/concepts/product-billing/git-lfs).

## Минимальная схема поставки

1. Версия вроде `base-audio-v1.0.0`, архив с четырьмя WAV, README об источнике/обработке и текстом CC BY 4.0. Лицензии и манифест остаются также в Git.
2. В Git закрепить конкретный URL версии и ожидаемый SHA-256 архива; не использовать `latest`. API GitHub содержит `digest` и `browser_download_url`, но установщик должен сравнивать скачанные байты с хешем, закреплённым в коде/манифесте, а не доверять только хешу, полученному вместе с архивом. [Release assets API](https://docs.github.com/en/rest/releases/assets).
3. Явная команда установки: скачать во временную папку, проверить SHA-256, разрешённые имена/число файлов и WAV, затем установить; при ошибке оставить прежний набор. Не перезаписывать личные пресеты. Никакой скрытой загрузки при импорте модулей или в тестах. Это предлагаемая реализация, ещё не сделанная.
4. Если включить immutable releases: создать draft, приложить и проверить все файлы, затем опубликовать. После публикации assets и связанный tag защищены от изменений; исправления выходят новой версией. Включать это после завершения очистки истории, чтобы не закрепить старую историю тегом. [GitHub: immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases), [включение настройки](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/establish-provenance-and-integrity/prevent-release-changes).

Существующий `tools/build_base_audio.py` уже проверяет SHA-256 оригинального Tech Live MP3 и результаты обработки. Его достаточно сохранить для воспроизводимой пересборки; новый генератор не нужен. Байт-в-байт соответствие WAV зависит от FFmpeg: текущая документация фиксирует 9.0.2. [Локальные сведения о сборке](../../assets/RIGHTS.md).

## Лицензии остаются разными

Код — MIT; Tech Live Kevin MacLeod и его переработанные фрагменты — CC BY 4.0. Вынесение в Releases не превращает музыку в MIT и не снимает атрибуцию. CC BY разрешает перераспространение и переработку, включая коммерческие цели, с указанием автора, источника/лицензии и изменений. Автор даёт шаблон кредита; сохранить его в архиве, документации и существующем UI. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/), [FAQ автора](https://incompetech.com/music/royalty-free/faq.html).

## Как сохранить прежний репозиторий безопасно

1. Сохранить приватную офлайн-копию истории и отдельно незакоммиченные изменения; составить список всех аудиопутей за всю историю и их переименований. Выполнять очистку в свежем отдельном клоне. Текущую рабочую папку с параллельными изменениями не фильтровать. `git-filter-repo` проверяет свежесть клона и предупреждает о необратимости операции; переименования автоматически не отслеживаются. [Руководство git-filter-repo](https://github.com/newren/git-filter-repo/blob/main/Documentation/git-filter-repo.txt).
2. Вычистить выбранные пути из всех предназначенных для публикации веток и тегов, затем проверить историю, объекты, refs и новый клон. Не оставлять в публикуемом репозитории резервную ветку/тег со старой историей. Добавить ignore для устанавливаемого набора; `.gitignore` не влияет на уже отслеживаемые файлы и не чистит историю. [gitignore](https://git-scm.com/docs/gitignore).
3. После проверки согласованно заменить конкретные remote refs, учтя защиты веток и открытые работы; старые клоны пересоздать либо тщательно очистить. Очистка меняет SHA затронутых коммитов, влияет на PR и подписи; старый клон способен вернуть удалённую историю. [GitHub: последствия переписывания](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).

Force-push не гарантирует уничтожения серверных копий: старые коммиты могут сохраниться в PR refs, кешах, чужих клонах и форках. GitHub отдельно пишет, что Support не удаляет несекретные данные в рамках процедуры удаления sensitive data; обещать через неё полное серверное стирание прежнего аудио нельзя. Перед открытием доступа нужен отдельный аудит доступных refs и прежних публикаций. [GitHub: границы удаления](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).

Исследование не выполняло переписывание/force-push, создание релиза или установщика; наличие старых GitHub-кешей и PR refs не проверялось.
