# Хуки и FM-анонсы: источники, фолбэки и план реализации

Статус: исходный проект после поиска по первичным источникам и локальных проб 25 октября 2026; реализованная экспериментальная v1 и более поздние продуктовые решения описаны в разделе 9. Разделы 1–8 сохраняют первоначальный план, включая ещё не выполненные критерии массовой проверки. [Проверка источников](../research/2026-10-25-hook-data-sources.md) отделена от этого проектного решения.

## 1. Конкретный выбор

**Один локальный кэш хуков, два пути подготовки, один безопасный путь в эфир.**

- Для carbonara: одобренный кэш → встроенный текст с метками припева → локальный Whisper → глобальное выравнивание всей последовательности текста → законченная фраза.
- Для записи без пригодного встроенного текста: одобренный кэш → локальный индекс готовых аннотаций / Songle → проверка временного соответствия → короткий фрагмент.
- При отсутствии пригодной разметки: All-In-One предлагает припев; слова/такты уточняют границы. PyChorus остаётся вариантом для инструментальных повторов, а не обязательным автоматическим fallback.
- Если готового приемлемого хука нет: обычная музыка, либо короткий голосовой анонс реально закреплённых песен без фрагментов. Случайный кусок на 40% песни не используем.

Это адаптивная цепочка, не обязательный вызов всех сервисов подряд. Для неизвестного внешним каталогам carbonara нет смысла сначала делать сетевой поиск каждого названия.

## 2. Как использовать готовые базы

| Источник | Как подключать | Что проверять | Если не сработал |
| --- | --- | --- | --- |
| Наши одобренные точки | Импортировать результаты прослушивания в SQLite; держать готовый локальный клип | Тот же аудиосигнал, диапазон, декодируемый файл | Перегенерировать клип по сохранённым точкам, если исходник тот же; при изменении аудио вернуть на проверку |
| Songle | Фоновый поиск по исходному YouTube URL; название — только способ найти кандидатов; сохранить response/revision | Ответ chorus содержит миллисекунды; источник, ревизия и соответствие нашей версии | 404 — кэшировать отсутствие; 429/5xx/таймаут — временная ошибка; не задерживать музыку |
| SongFormDB | Скачать только JSONL аннотаций, построить локальный индекс по YouTube-ID; не тянуть спектрограммы/аудиодатасет | Частичная или полная разметка, исходный тип секции, версия и происхождение | Нет подходящей секции/ID — перейти к локальному анализу |
| Harmonix Set | Небольшой дополнительный локальный индекс: MusicBrainz/AcoustID ID, названия, сегменты и такты | Идентичность и временное выравнивание, не одно совпадение названия | Не считать обязательным: текущий поиск по метаданным не покрыл нашу локальную фонотеку |
| SALAMI / RWC / McGill Billboard | Исследовательские/дополнительные импортеры после первой версии, если реально повышают покрытие | Разные схемы секций и версии записей; условия использования конкретного набора | Не блокировать запуск первой версии отсутствием этих адаптеров |
| Hooks Unlimited | Сейчас исключён по твоему решению: аккаунта нет | Доступ к каталогу, условия получения и применения материалов не проверены | Никакого runtime-зависимого запроса или покупки |

SongFormDB-Hook — не готовая массовая библиотека рекламных хуков: у Starboy в нашем совпадении есть только куплет, у Promesses пригодный отрывок обозначен как instrumental. Сохраняем тип секции, не переименовываем любую аннотацию в «припев». В наших пробах оба экспортированных датасетных фрагмента и три Songle-фрагмента получили одобрение, но это доступные совпадения, а не оценка покрытия каталога. [Наши результаты](../../spike/music-hooks/results/DATABASE-USER-RESULTS.md), [формат SongFormDB](https://huggingface.co/datasets/ASLP-lab/SongFormDB).

### Границы доступа и лицензий

Songle проверен конкретными успешными REST-запросами; наличие ответа не означает SLA или разрешение зеркалировать весь каталог. Условия явно регулируют видимый Widget и коммерческое применение; отдельное разрешение на массовый backend-кэш REST-разметки в них не установлено. Для личного пилота используем точечный lookup и provenance, не создаём скрытый виджет и не регистрируем массово песни. Для поставляемой внешним пользователям интеграции условия REST-кэша нужно уточнить; до этого уже полученные и одобренные локальные клипы не зависят от постоянной доступности Songle. [API](https://widget.songle.jp/docs/v1?lang=en), [условия](https://widget.songle.jp/docs/terms-of-use).

SongFormDB указывает CC BY 4.0, SALAMI — CC0, актуальный репозиторий RWC-аннотаций — CC BY-NC 4.0; хранить attribution/provenance при импорте. Для Harmonix отдельно различать LICENSE репозитория и лицензию архива спектрограмм. Первая версия не требует скачивания спектрограмм и не распространяет оригинальные музыкальные записи. Точные источники лицензий — в [исследовании](../research/2026-10-25-hook-data-sources.md).

### Опознание записи не равно выравниванию времени

Для локального файла сначала читаем имеющиеся Recording MBID / ISRC / YouTube-ID, если они есть. Для неизвестной внешней музыки можно добавить Chromaprint → AcoustID → Recording MBID. AcoustID требует ключ приложения, бесплатный публичный API ограничен некоммерческим использованием и тремя запросами в секунду; его регистрацию и активацию не делаем обязательными для запуска carbonara. [AcoustID API](https://acoustid.org/webservice).

AcoustID и MusicBrainz не возвращают готовые хуки и не гарантируют совпадение временных отметок: MusicBrainz может считать некоторые отличия мастеринга одной Recording. Даже совпавший YouTube-ID может ссылаться на изменённый позднее монтаж. [Правила MusicBrainz Recording](https://musicbrainz.org/doc/Style/Recording), [Chromaprint](https://github.com/acoustid/chromaprint).

Правило импорта:

1. Название/исполнитель находят кандидатов, но не разрешают применение таймкодов.
2. Совпавшие ID и близкая длительность повышают вероятность нужной записи, но сами по себе не дают статус APPROVED.
3. Если есть исходный звук разметки, сопоставить его с нашим аудио и проверить начало, середину и конец предполагаемого клипа. Наш DTW-перенос — уже рабочий кандидат для этого, но его пороги пока экспериментальные.
4. Если исходного звука нет и временное соответствие не подтверждено, импортировать только как CANDIDATE для прослушивания, а не как готовый к автоматическому эфиру клип.
5. После одобрения сохранить именно локальные таймкоды и локальный аудиосигнал; на следующем старте внешний сервис уже не нужен.

## 3. Матрица фолбэков

| Ситуация | Следующее действие | Чего не делать |
| --- | --- | --- |
| Есть одобренный хук для неизменившегося аудио | Использовать его; проверить готовность файла перед постановкой | Повторно анализировать трек или перезаписывать ручной выбор |
| Есть полный встроенный текст и метки припева | Whisper с кэшированием → выравнивание всего текста → фраза с границами строк | Искать первое отдельное совпадение припева в начале песни |
| Заголовки нестандартные | Нормализовать заголовки с номерами/описаниями; pre-chorus/post-chorus оставить отдельными | Считать любое вхождение слова chorus припевом; объявлять остальные 27 carbonara «без припева» |
| Текст совпадает плохо или границы сомнительны | Один фоновый повтор распознавания выделенного вокала; при необходимости сравнить All-In-One | Бесконечно повторять ASR, менять пороги до получения любого ответа |
| Нет пригодного собственного текста | Проверить готовые аннотации; LRCLIB может дать синхронизированный текст как дополнительную подсказку | Считать одинаковую длительность подтверждением версии |
| Готовых аннотаций нет | All-In-One с одной моделью; выбрать подходящий участок внутри секции и осмысленные границы | Считать весь найденный chorus готовым рекламным хуком |
| Инструментальная запись | Готовая разметка instrumental/drop или повтор PyChorus + прослушивание | Требовать вокальный припев или автоматически ставить любой повтор |
| Текст/анализ/провайдер не дали приемлемого результата | REVIEW_REQUIRED или NO_HOOK; продолжать обычную музыку | Вырезать случайную середину песни или заполнять ожидание тишиной |
| Ошибка сети / 503 / 429 | Отложить повтор с backoff, использовать локальный кэш или следующий путь | Записать вечное «песни нет в базе» из-за временной ошибки |
| Сменился исходный аудиосигнал | Инвалидировать привязку точек и готовый клип; подготовить заново | Переносить старое пользовательское одобрение на другую версию песни |
| Изменилась очередь до выхода анонса | Снять устаревший анонс и подготовить новый либо пропустить | Озвучить обещание песни, которой уже нет в закреплённом блоке |

Предлагаемые начальные политики кэша, не требования провайдеров: отсутствие результата — 7 суток, временные ошибки — 1/5/30 минут до следующей попытки, блокировка авторизации — до изменения подключения. Пользовательский refresh снимает отрицательный кэш. Успешные аннотации сохраняются с ревизией и временем получения; фоновые обновления создают новые кандидаты и не заменяют одобренный клип.

## 4. Данные и минимальная реализация

Расширяем существующий SQLite, не вводим отдельный сервис/векторную базу/очередь задач.

**`track_hooks`:** ссылка на трек, идентичность аудио, хэш текста, версия алгоритма, start/end, источник и provenance JSON, review = CANDIDATE / APPROVED / REJECTED, путь готового клипа, время создания. Разные припевы можно хранить разными строками; один явно выбранный активный хук, альтернативы не удаляются.

**`hook_lookups`:** provider + lookup_key, outcome = HIT / MISS / TEMP_ERROR / AUTH_REQUIRED / AMBIGUOUS, response JSON, retry_after, updated_at. Оценки провайдера, доля совпавших слов и факт пользовательского одобрения остаются разными полями — не сводим их в искусственную общую вероятность.

Идентичность: существующая file-signature — дешёвый сигнал изменения; при первом анализе/изменении фоново хэшируем стандартно декодированный PCM и сохраняем формат/версию декодера. Перезапись тегов без изменения PCM не должна лишать уже одобренное аудио статуса. Изменение текста инвалидирует автоматические текстовые результаты, но не ручное одобрение неизменившегося клипа. Смена модели не меняет ранее одобренный хук без проверки.

Распределение кода:

- `radio/hooks.py`: поиск готового/одобренного хука, провайдерные lookup, сохранение/выбор кандидатов и проверка актуальности.
- Отдельный фоновый worker/команда анализа: переиспользует наш глобальный aligner, локальный Whisper и FFmpeg; одна тяжёлая работа за раз с низким приоритетом. Никаких загрузок моделей при переходе между песнями.
- `radio/store.py`: небольшие миграции двух таблиц.
- `radio/plugins.py`: один выключенный по умолчанию эксперимент Coming up / Track previews; переключатель использует существующую сохранённую схему Experiments.
- `radio/daemon.py` и `radio/engine.py`: только готовые клипы, проверка закреплённой очереди и отмена устаревшего анонса; без ASR/HTTP внутри handoff.
- `radio/timeline.py`: отдельное событие MUSIC_TEASER; фрагмент песни не становится MUSIC_STARTED и не помечает целый трек прослушанным.

## 5. Эфирное поведение первой версии

Стартовые продуктовые параметры: не чаще одного анонса в 30 минут, два будущих трека, каждый хук 5–12 секунд, короткая фраза ведущего между фрагментами. Это наши настройки для проверки, а не отраслевой норматив. При наличии только одного приемлемого хука допустим короткий анонс одного трека; пустой анонс не создаётся.

До синтеза ведущего закрепляем набор будущих песен и создаём идентификатор обещания `(generation, track_refs, audio_versions, cue_ids)`. В текущем коде `upcoming_music()` явно обещает достоверность только первого shuffle-трека; поэтому его список не может быть основанием анонса двух песен. Нужна небольшая операция подготовки закреплённого блока поверх существующей `fresh`-очереди с готовыми локальными файлами. [Текущий контракт](../../radio/engine.py).

Перед постановкой и непосредственно перед выходом проверяем: тот же набор и версия очереди, файлы загружены, хук соответствует аудио, голоса готовы, переключатель включён, есть речевой бюджет. Используем существующие `handoff_lock` и `schedule_generation`, а не параллельный несогласованный планировщик. Подготовку речи учитываем в существующем лимите речи; музыкальные фрагменты не считаем речью.

Пути смены источника, reroll, `_clear_fresh`, Next, pause/stop и исчезновение загруженного трека должны отменять ещё не прозвучавший анонс, если его обещание стало неактуальным. Если пользователь меняет очередь уже после прозвучавшего обещания, выполняем его команду и фиксируем отмену обещания в истории, не принуждаем слушать прежний источник.

Если к моменту перехода нет готового хука: можно произнести только названия подтверждённых будущих треков. Если не готов голос или сама будущая очередь не подтверждена — пропустить весь анонс. Текущий/следующий обычный трек продолжается существующим путём, включая местный fallback при загрузке YouTube; дополнительные синхронные ожидания не добавляем.

## 6. План работ и критерии готовности

| Этап | Конкретный результат | Проверка перед переходом дальше |
| --- | --- | --- |
| 1. Зафиксировать кэш и provenance | Импорт нынешних одобренных клипов, отдельные кандидаты/отказы, идентичность аудио; никаких изменений эфира | Старые оценки сохранены; смена аудио инвалидирует старые точки; offline reuse без запросов |
| 2. Проверить основной путь carbonara | Нормализация меток + глобальное выравнивание на 20 новых треках из оставшихся 178 | Предлагаемый продуктовый порог: минимум 18/20 одобрены без сдвига; остальные явно REVIEW/NO_HOOK, не принудительно «успешны»; повторные припевы и границы проверены слухом |
| 3. Импортировать готовые базы | Songle adapter + локальный SongFormDB/Harmonix index; identity/таймлайн проверяются до допуска | 10 заранее выбранных сторонних записей: отдельно измерены покрытие, верная версия, качество клипа; тест ms→s, 404, 503, неоднозначного имени, неверного монтажа |
| 4. Добавить ограниченные фолбэки | All-In-One для неуверенных/безтекстовых случаев, PyChorus только как проверяемый кандидат для инструментала; bounded retry | Сетевой сбой не превращается в MISS; неудача одного анализатора не ломает другой; нет бесконечных повторов |
| 5. Подключить эксперимент FM-анонсов | Один выключаемый переключатель, локально готовый монтаж и согласованное закрепление будущих песен | В изолированном RADIO_DATA_DIR записан эфир: обычный переход, Next, pause, source switch, reroll, недоступный файл, выключение фичи; нет старого обещания и тишины; событие истории подтверждает реальный выход |

Порог 18/20 — предлагаемое условие небольшого пилота, не статистическое доказательство 90% надёжности. До первого измерения считаем новые автоматические результаты кандидатами; не переносим четыре удачных carbonara на все 182.

Новые модели WhisperX/другой phonetic aligner испытывать только на оставшихся проблемных случаях, сравнивая реальные границы с текущим решением. WhisperX действительно добавляет акустический alignment, но его документация описывает ограничения словаря и наложения речи; превосходство на пении carbonara мы не измеряли. [WhisperX](https://github.com/m-bain/whisperX).

## 7. Что сознательно не входит в первую версию

Нет обучения собственной модели, обязательного AcoustID-аккаунта, HookSelect, ансамбля восьми All-In-One, загрузки всего аудио/SongFormDB-спектрограмм, постоянного опроса всех сервисов и автоматического угадывания припева по проценту длительности. Отдельно не строим чарт/топ или новый музыкальный scheduler: это другие функции.

Лицензия аннотации, доступ к API и право использования конкретного аудио — разные свойства источника; при импорте сохраняем источник/ревизию/лицензию данных. Этот план не меняет распространение пользовательской музыки и не публикует локальные клипы.

## 8. Основание решения и оставшиеся проверки

Наши оценки: Songle 3/3 доступных клипа, SongFormDB 2/2, carbonara local text 3/4 до глобального выравнивания; после выравнивания — один новый одобренный вариант и три byte-identical ранее одобренным. PyChorus: 2 готовых / 6 с правками / 2 отвергнутых. All-In-One: 3 готовых / 3 с правками / 1 отвергнутый / 1 без кандидата. [Подробный локальный анализ](../../spike/music-hooks/results/ANALYSIS-RU.md).

На момент исходного проекта production-кэш и эфирные анонсы ещё не были реализованы; актуальное состояние v1 — в разделе 9. Массовая проверка carbonara, отдельный phonetic aligner и fingerprint-покрытие внешних баз остаются отдельными незавершёнными этапами.

## 9. Реализованная экспериментальная v1

Обновление 27 октября: Coming up завершает новостной блок, а не прерывает музыку самостоятельным двойным анонсом. Порядок: новости → короткое представление более поздней песни и один её хук → представление первой песни → первая песня целиком. Хук первой песни не повторяется перед её запуском. Без подходящего хука звучит только представление первой песни; общий предел — 25 секунд. Слишком короткий блок, недостаток речевого бюджета или неподготовленная очередь означают пропуск анонса, без задержки музыки. Эксперимент по умолчанию выключен; после установки нужен перезапуск станции.

Две готовые песни закрепляются существующим snapshot очереди, но объявленными считаются только фактически названные. Native handoff проверяет также идентичность предшествующего новостного блока: при смене очереди или источника, пропуске новостей и отключении эксперимента анонс отменяется. Обычный Shuffle и ручные команды сохраняют силу. Склейка голоса и музыки сохраняет stereo 44.1 kHz; формат mono 24 kHz первой голосовой реплики не переносится на хук.

- `radio/hooks.py` и `radio/hook_alignment.py`: постоянный SQLite-кэш, идентичность по PCM 44.1 kHz stereo s16, сохранение ручных решений, атомарные клипы, embedded lyrics → глобальное выравнивание, точечный Songle, нормализованный локальный индекс аннотаций, необязательный All-In-One. AUTO требует общего покрытия текста ≥0.75 и покрытия фразы ≥0.95; это начальные экспериментальные пороги, не доказанная точность. Остальные найденные фрагменты требуют прослушивания. Нет уверенного фрагмента — NO_HOOK; ошибка ASR/временная ошибка сервиса — ERROR с повтором.
- `radio/daemon.py`: одна фоновая задача анализа за раз; вся локальная библиотека и готовые файлы YouTube. Отдельно готовится только монтаж, без второго музыкального scheduler. Речь учитывается в общем бюджете. Синтез не удерживает handoff lock; перед передачей проверяются поколение, состояние и точный snapshot.
- `radio/radio.liq`: резерв второй локальной песни без перестановки хвоста, native snapshot готовых запросов, проверка обещания перед передачей, явная отмена по ID. Snapshot учитывает запрос, уже вынутый в буфер движка, но ещё не прошедший событие эфира. Shuffle сохраняет подготовленную очередь.
- История использует MUSIC_TEASER; такие фрагменты не создают MUSIC_STARTED и не делают целые песни прослушанными. После прозвучавшего обещания ручные команды пользователя сохраняют силу.
- UI Experiments показывает Coming up и Music hooks: прослушивание, одобрение, отказ. Доступ к аудио требует существующего токена, путь ограничен кэшем хуков.

Проверка v1: изолированный эфир подтвердил анонс → Next → первую обещанную песню, а также отбрасывание анонса после замены следующего трека; прошли проверки кэша, отмены, бюджета речи и UI. В изолированный кэш импортированы 8 прежних одобрений с проверкой исходного trial hash и PCM. На новом carbonara «3%» локальное распознавание прошло, но подходящих границ фразы не нашлось: NO_HOOK и голосовой fallback. Это не проверка качества на 20 новых песнях и не прослушивание массового автоматического эфира. Raw-импортеры SongFormDB/Harmonix, DTW-перенос и отдельный phonetic aligner остаются следующим этапом.
